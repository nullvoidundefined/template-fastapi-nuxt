## Architectural decisions

**Five PRs rather than three.** Chosen because the rate limiter carries the slice's only real threat model, the `X-Forwarded-For` trust chain, and a review of it should not share a sitting with CORS configuration. The alternative, folding rate limiting in with the other middleware as one "remaining middleware" PR, matches the spec's own one-line description of the slice and would have been about 800 lines in one diff. The spec describes what the slice delivers, not how many review units it takes, so splitting does not depart from it.

**The CI chores land first, not last.** Chosen because the Docker build cache shortens the two slowest jobs on every one of the four PRs behind it, so paying for it first returns the time within the slice. The alternative, landing them last, would keep the acceptance criteria unblocked by a configuration change, which is the reason the owner was offered that ordering at Gate 1 and declined it.

**B-43 is refactored rather than reimplemented.** Slice 01's body-size guard already answers 413 in the envelope, with its code and message as local string constants in `app/middleware/request_context.py`. Chosen: PR 2 re-homes those two constants onto the registry and leaves the behavior alone, so the existing tests passing unchanged is the evidence that nothing moved. The alternative, rewriting the guard against the new registry, would have replaced working, reviewed code and left no such evidence.

## Reflection

Time since implementation: the first commit landed at 08:27 UTC and this document was written at 08:46 UTC, about nineteen minutes later.

What I understand now that I did not at the start: the acceptance criteria are not evenly weighted, and the slice's shape follows the weighting rather than the criteria count. B-7 alone is one PR because a limiter keyed on a header a client controls is not a limiter, and that is a property a reviewer has to check by reading the key derivation end to end, not something a passing test suite demonstrates on its own.

What I got wrong first: two things, and the second was the serious one.

The header said 3.5 hours while the PR blocks I wrote alongside it summed to 3 hours 45 minutes, and I committed the document before checking the arithmetic. Re-estimating PR 1 from 35 to 50 minutes, which the two deferred CI items honestly need, moved the total to 4 hours, and the second commit made the document and both tickets agree on that number.

Worse, PR 4's middleware chain was wrong in a way that would have broken an acceptance criterion slice 01 already satisfies. I ordered the chain with `RequestContextMiddleware` innermost, reasoning about which guard should bound which other guard's time, and missed that the structlog binding of `request_id` lives inside that class. Every log line the security-headers, CORS, rate-limit, CSRF, and timeout classes emit would have run outside the binding and carried no request ID, which is exactly what B-2 forbids, and the ordering test I specified checked response headers only, so it would have passed anyway. The Python track fixes the chain at positions 1a to 7 with the request context at 1b, and slice 01 already built it that way; I reasoned from first principles where a convention file had already settled it. The corrected plan restores the track's order and adds the assertion that a guard rejection's log line carries `request_id`, which is the assertion that actually fails when the order is wrong.

I also told the owner that Linear needed authorizing before the tickets could be opened. It did not. The `design` plugin ships a second, unauthorized Linear server, and its name in the session's unauthorized list looked like the whole story; `claude mcp list` showed the claude.ai Linear connector already connected. The lesson is to check the tool surface before reporting a capability as unavailable, which is what the session's own instructions already say to do.

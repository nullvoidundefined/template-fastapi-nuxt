# PR: Frontend skeleton and workspace (slice 01 PR 2)

Ticket: IAN-125 (slice IAN-123). Branch: `feat/slice01-frontend-skeleton`. Spec: `docs/superpowers/specs/2026-09-19-template-fastapi-nuxt-design.md`, criterion B-49. Plan: `docs/slices/slice-01-walking-skeleton.md`, PR 2.

## Summary

This PR adds the Node side of the template: a pnpm workspace at the root, the Nuxt 4 app at `apps/client/web` with its landing page and its own health route, and the `packages/tokens` design tokens that every later page styles itself with. The backend from PR 1 is untouched. After this PR, `pnpm dev` starts the API and the web app together, and `/` renders the landing page with links to log in and register.

## What changed

- **Workspace:** the root `package.json` (with `dev`, `dev:api`, and `dev:web` scripts), `pnpm-workspace.yaml` covering `apps/client/*` and `packages/*`, and Prettier configuration (4 spaces, single quotes, width 100).
- **`apps/client/web`:** a Nuxt 4 app with `nuxt.config.ts` (SSR on, `<html lang="en">` and a default title through `app.head`, `runtimeConfig` declaring `apiBaseUrl` with an empty default so one image serves every environment), `app/app.vue` (layout plus page, and a title template that appends the product name), `app/layouts/default.vue` (header and `<main>`, no `<h1>`), `app/pages/index.vue` (the landing page, with its title and description through `useSeoMeta`), each with `<script setup lang="ts">` first and its styles in a sibling `.module.scss`, `app/assets/css/main.scss` (the tokens plus base rules, focus outlines, and reduced motion), and the Nitro route `server/api/health.get.ts`. ESLint through `@nuxt/eslint` carries the Vue track's rules at error level (`vue/block-order`, `vue/define-macros-order`, `vue/no-v-html`) and the `eslint-plugin-vuejs-accessibility` recommended set; `vue-tsc` and Vitest with `@nuxt/test-utils` are configured. The web `build` script builds the tokens package first, so `nuxt build` never runs without `dist/_tokens.scss`.
- **`packages/tokens`:** `tokens.ts` is copied from `template-express-next`, with one change: the accent is darkened from `#e8651a` to `#bf4f10` and its hover from `#c85411` to `#a8440c`, because white text on the old accent measured 3.33:1 against the 4.5:1 WCAG AA floor (the owner chose this fix over dark text on the accent). The SCSS generator is split into a pure `generateTokensScss(tokens)` and a build step, `writeTokensScss.ts`, that writes `dist/_tokens.scss`. A `prepare` script builds the package on every install, so `main.scss` can `@use '@repo/tokens/scss'` without a manual step.
- **Root Vitest config:** `vitest.config.ts` with `projects: ['apps/client/web', 'packages/tokens']`, and `vitest` as a root dev dependency, so `tdd.sh`, CI, and editors all run the whole Node suite from the repository root.
- **Product docs (R-607):** the web health and landing rows in `docs/feature-list/features.md`, US-INFRA-003 in `docs/user-stories/infrastructure.md`, US-LANDING-001 in `docs/user-stories/landing.md`, and `e2e/landing.spec.ts`.

## Architectural decisions

- **The token generator now covers every group, not only colors and transitions.** The slice plan said to port the package unchanged, but the Express generator emits only colors and transitions, so font sizes, weights, radii, and spacing would exist in `tokens.ts` with no way to reach the styles. The generator therefore emits every group with a fixed prefix per group (`--font-size-body`, `--radius-card`, `--spacing-4`), and the test derives the expected names from the token object itself, so a token added later cannot be silently dropped. Apart from the two accent colors described above, the token values are unchanged. This is a scope change from the plan, recorded here and in the PR 2 section of the slice plan.
- **Pure generator, separate build step.** The Express generator wrote the file at import time, which made it untestable without touching the file system. Splitting it keeps the tested function free of I/O.
- **Tokens build on install through `prepare`, and `dist/` stays ignored.** The alternative was committing the generated SCSS, which the Express template also avoids; committing it would let the file drift from `tokens.ts`. The cost is that any install, including in Docker (PR 4), must run lifecycle scripts for the workspace packages.
- **Web tests live under `tests/nuxt/`.** That is the directory Nuxt's generated `tsconfig` already includes, so `vue-tsc` type-checks the tests as well as the app. The alternative, `__tests__/` beside each file per R-313, would need a second tsconfig for the test files and fights Nuxt's own layout.
- **The Nuxt test environment's `rootDir` is pinned to the web app's own directory.** `@nuxt/test-utils` otherwise looks for the Nuxt app in the current working directory, which is the repository root when the root projects config runs it.
- **The web health route never calls the backend.** A backend outage should fail the API's readiness probe, not the web container's liveness check, or the orchestrator would restart a healthy web server.

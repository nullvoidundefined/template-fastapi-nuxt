# Slice 02, PR 3: Alembic, the users table, and the connection dependency

**Ticket:** IAN-169
**Branch:** `feat/slice02-alembic-users`
**Plan:** `docs/slices/slice-02-data-and-errors.md`, the PR 3 block
**Stories:** US-INFRA-006, with an amendment to US-INFRA-005

## Summary

Before this pull request the application could start, answer two health routes, and fail in a
consistent envelope, but it had no schema, no way to create one, and no request that ever held a
database connection. This change closes all three gaps at once, because none of them is useful
alone: a migration chain with nothing to migrate, a table no request can write to, and a
transaction boundary over a schema that does not exist are each half a feature.

Three things land. Alembic arrives as a runtime dependency with its configuration, its environment
module, and the first revision, which creates the shared `set_updated_at` trigger function, the
`users` table, the unique index on `lower(email)`, and the trigger. `get_connection` gives every
data-bearing route one connection inside one transaction per request. And the places a migration
has to run before a deploy exists, which is compose locally and in the two container CI jobs, the
integration fixture, and the end-to-end suite's global setup, all reach head through the same
chain rather than through a path each invented for itself.

## What changed

- **`apps/server/alembic.ini`, `migrations/env.py`, `migrations/script.py.mako`.** The
  configuration carries no `sqlalchemy.url`, because the URL is a secret and does not belong in a
  checked-in file (R-102); `env.py` reads it from the application's own `Settings` unless a caller
  set the option in memory first, which is how the integration fixture points the same chain at
  `TEST_DATABASE_URL`. The chain runs through the async engine, on a `NullPool` engine disposed in
  a `finally`, because the process exits as soon as the chain finishes.
- **`migrations/versions/20260923_0001_create_users_and_set_updated_at.py`.** Written by hand
  rather than from an autogenerated draft, because autogenerate produces none of the three things
  that matter here: a PL/pgSQL function, a unique index over an expression, and a trigger. The
  `role` column is deliberately absent; the data model assigns it to slice 05.
- **`app/db/tables.py`.** The one `MetaData`, with a naming convention that names every index and
  constraint from the table and column it covers, and the `users` table Alembic compares against.
- **`app/db/session.py`.** `get_connection`, declared at every call site as
  `Depends(get_connection, scope="function")`. It also classifies a failed connect as a
  `DatabaseUnavailableError`, which is the correction IAN-169 carried in from the PR 2 reviews.
- **`app/main.py` and `app/errors.py`.** `ConnectionError` and `socket.gaierror` come off the
  global handler set, and `DatabaseUnavailableError` joins the `AppError` family.
- **`apps/server/Dockerfile`, `docker-compose.yml`, `playwright.config.ts`, `e2e/global-setup.ts`.**
  The image copies `alembic.ini` and `migrations/`; a one-shot `migrate` service runs
  `alembic upgrade head` on that image, and `api` and `worker` wait on it through
  `condition: service_completed_successfully`; the end-to-end suite runs the same service before
  its first spec.

## Architectural decisions

**Where a failed connect is classified.** Chosen: inside `get_connection`. Alternative: keep
`ConnectionError` and `socket.gaierror` registered globally in `app/main.py`, as PR 2 left them.
Why: `builtins.ConnectionError` is the base class of every socket peer failure, not just a
database one. While it was registered globally, any route that raised a bare `ConnectionResetError`
from an outbound HTTP call or from Redis answered 503 `SERVER_DATABASE_UNAVAILABLE`, which tells
the client to retry against a healthy database and points the operator at the wrong dependency.
Nothing in the codebase raised it yet, which is why PR 2 could ship with it, and removing it before
`get_connection` existed would have regressed B-9, because a refused connect raises
`ConnectionRefusedError` that SQLAlchemy never wraps. `get_connection` is the one place a request
opens a connection, so it is the one place that can say a connect failed without guessing.
`OperationalError` stays registered globally: it is a SQLAlchemy type that no non-database code
path can raise, so it carries no ambiguity to remove.

**How a failed commit is proven to change the response.** Chosen: a real deferred unique
constraint on a probe table the test creates and drops. Alternative: patch the connection's
`commit` to raise. Why: the assertion is about _when_ the commit runs relative to the response,
and a patched commit proves only that a raised exception becomes a 500. A `DEFERRABLE INITIALLY
DEFERRED` constraint fails at `COMMIT` the way a deferred violation does in production, so the
test fails for the real reason if `scope="function"` is ever dropped from the dependency.

**Where the migration runs.** Chosen: a one-shot compose service on the API image. Alternative:
running `alembic upgrade head` from the application's own startup, or from a checkout in CI. Why:
a migration at startup runs once per replica and races itself, and a migration from a checkout
never proves the image can run one, which is exactly what Railway's `preDeployCommand` will need
in slice 08. Running it on the image means a missing `COPY` fails `docker compose up` rather than
the first deploy.

**How the connection is released.** Chosen: `close()` in a `finally`, around an
`async with connection.begin()`. Alternative: `async with connection, connection.begin()`. Why:
`engine.connect()` returns a connection that is already started, so entering it as a context
manager starts it a second time and raises `InvalidRequestError: connection is already started`
before the route ever runs. This was caught by the rollback test rather than by review.

## Testing

Ten new tests, all authored by Codex through `codex exec` (R-907), proved red before any
implementation existed and green after.

- **Integration, against the real Postgres:** `upgrade head` then `downgrade base` leaves no
  `users` table and no `set_updated_at` function; an update moves `updated_at` and leaves
  `created_at` unchanged; two addresses differing only in case violate the unique index; a handler
  that returns leaves exactly one row; one that raises leaves none; and a deferred violation raised
  at `COMMIT` answers 500 with nothing persisted.
- **Unit:** a route taking `get_connection` against a closed port answers 503
  `SERVER_DATABASE_UNAVAILABLE` under both production and development; a route raising a bare
  `ConnectionResetError` answers 500; and every `server_default` in every revision takes an allowed
  source form (R-328).
- **Removed:** PR 2's `test_b9_refused_connect_answers_503_server_database_unavailable`, which
  asserted the behavior this pull request deliberately changes. Its coverage moves to the
  `get_connection` test above rather than disappearing.
- **The image** is covered by the `docker-build` job rather than by a unit test. Verified locally
  as well: `docker compose run --rm migrate alembic downgrade base` drops `users`, and the plain
  `migrate` service brings it back, both through the built image.
- Full server suite: 120 passed. `ruff`, `black`, and `mypy --strict` clean.

## Reflection

What is clearer now than at the start: the argument in IAN-169 is not really about which exception
types to register, it is about where a classification is allowed to be made at all. A global
handler keyed on a builtin exception class is a guess about what the exception meant, and it is
wrong exactly as often as some other subsystem happens to raise the same class. Moving it to
`get_connection` did not make the rule more accurate, it removed the guess.

What was wrong first: the connection lifecycle. `async with connection, connection.begin()` reads
like the obvious spelling and is wrong, because `engine.connect()` has already started what the
first context manager would start. The rollback test caught it, and it would not have been caught
by review, which is a small argument for writing the rollback case rather than assuming the happy
path generalizes.

Also worth recording for the process rather than the code: the tests in this pull request were
written twice. The first set was written by the implementing model under time pressure, in breach
of R-907, and the guard that exists precisely to prevent that fired on every file and was
click-confirmed through rather than heeded. They were then re-authored by Codex from the plan.
The rule held; the person driving had to enforce it, which is the failure mode the rule was
written to avoid.

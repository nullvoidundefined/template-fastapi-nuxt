# Stack

This catalog lists every significant language, runtime, framework, library, tool, service, and
infrastructure piece this application uses, grouped by layer. Versions are the pinned or minimum
version each manifest declares, read from the manifests themselves
(`apps/server/pyproject.toml`, `apps/client/web/package.json`, the root `package.json`,
`packages/*/package.json`, the three Dockerfiles, `docker-compose.yml`, and
`.github/workflows/ci.yml`) rather than assumed. "Why chosen" cites the design spec's "Decisions
already made" table
(`docs/superpowers/specs/2026-09-19-template-fastapi-nuxt-design.md`) and the Python and Nuxt
convention tracks where either gives a reason; where neither does, the entry says so rather than
inventing one.

This document reflects the code on the branch that carries every slice through slice 08: billing
(Stripe checkout, the customer portal, the webhook ledger, and stripe-mock), observability and
integrations (Sentry, PostHog, Resend, R2), and closing work (the three Railway configuration
files, the smoke suite, Lighthouse as a development dependency, and the hourly
`delete_expired_rows` cleanup job).

## Billing

- **SDK.** `stripe>=15.6.1` (see the Backend API table above) creates Checkout sessions in
  subscription mode and billing-portal sessions, and verifies webhook signatures with the SDK's
  own signature check, which needs no network call and no API key.
- **Signature verification.** `apps/server/app/services/billing/verify_webhook_event.py` reads the
  raw request body (never the parsed JSON, because re-serializing would change the bytes Stripe
  signed) and the `Stripe-Signature` header, and calls the SDK's `construct_webhook_event` with
  `settings.stripe_webhook_secret`. A missing signature or an unset signing secret answers 400
  `BILLING_WEBHOOK_MISCONFIGURED`; a signature that does not verify answers 400
  `BILLING_WEBHOOK_INVALID_SIGNATURE`.
- **The webhook ledger.** `billing_webhook_events` records one row per Stripe event ID, moving
  through `claimed`, then `processed` or `failed` (`apps/server/app/constants/billing.py`'s
  `BillingWebhookEventStatus`). A claim older than ten minutes is taken over by a redelivery, so a
  handler that crashed mid-processing does not block Stripe from retrying forever; a handler
  failure marks the event `failed` and answers 500 `BILLING_WEBHOOK_PROCESSING_FAILED` so Stripe
  redelivers it. The hourly cleanup job (see Worker above) deletes ledger rows older than 30 days.
- **stripe-mock.** `docker-compose.yml`'s `stripe-mock` service runs `stripe/stripe-mock:v0.203.0`,
  started only with `docker compose --profile e2e up`, published on loopback only, so the
  end-to-end suite exercises checkout and the portal without a real Stripe account.
- **Without configuration.** `STRIPE_SECRET_KEY` unset answers 503 `BILLING_NOT_CONFIGURED` on
  checkout and portal rather than failing on the first Stripe call.

## How to keep this current

Update this document in the same task that adds, removes, majorly upgrades, or replaces anything
listed here. A dependency bump that changes only its patch or minor version does not need an
entry change unless the reason it was chosen also changed; adding a new library, dropping one, or
moving to a materially different major version does.
